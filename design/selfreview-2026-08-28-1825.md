## P0 — 不修复则正式矩阵数据不可辩护

1. **num_ctx 四家全不一致,RESULTS.md 公平性声称失实(本轮最大新发现)**
   - 发现: RESULTS.md:4 写"4 agent 同模型同 num_ctx=32K",但实测各 adapter 上下文完全不同:
     - hummingbird = **16384**(ollama_agent.py CTX_BUDGET 默认;run_bench 未设 `AGENT_CTX`);
     - opencode = ornith-35b→32768, gemma4 e2b/12b→**131072**, qwen3.5 4b→**131072**(config 实测);
     - agent-mini = **ollama 默认**(config.json 无 num_ctx 键,大概率 2048/4096);
     - goose = 默认(未设)。
   - 影响: 上下文窗口是长任务 agent 最敏感变量之一(LRAB 全 8+ 步工作流),四家不在同一 ctx 上比较,
     声称"同 num_ctx=32K"逐字失实。agent-mini 被默认 4K 重度 handicap——其 e2b=0.857 反而说明若对齐会更高,
     opencode 12b 在 128K 下仍 0.0,更没法辩护。这条是论文/HN 发布的致命伤。
   - 怎么改: ①每家 adapter 显式钉死 num_ctx=32768(hummingbird 在 run_bench 设 `AGENT_CTX=32768`;
     agent-mini config 加 `num_ctx: 32768`;goose 查其 ctx 配置项并设置;opencode 已可);②run 时把实际
     num_ctx 写进 score.json(可执行回查);③RESULTS.md 改为披露真实值或等统一后重跑。

2. **静默失败被记 "completed" 且 total=0.0,正在污染发布矩阵(正在发生)**
   - 发现: opencode gemma4:12b 格(181533, 18:23)transcript 只有 `Glob "*" 2 matches → Read task_input.txt`,
     之后 460s 无任何动作、exit=0、零产物,score 0.0,但 failure_mode="completed"。classifier 的
     `wall<30→early_finish` 和 `not os.listdir→no_artifacts`(workdir 有 task_input.txt 所以不命中)都套不中,
     静默放弃被当"正常完成"。
   - 影响: 这种 0.0 不是"能力差",是 harness/模型静默终止;按现状会作为合法能力 0 分进入矩阵。审稿人翻
     transcript 即可拆穿("读入任务后什么都没做")。
   - 怎么改: classifier 增加 stall/surrender 检测(transcript 含 Read 任务后无后续 tool call 且 0 产物 →
     failure_mode="stall");与 crash 同规则,不进均分、单独披露。roadmap §3.3 的失败模式分类已要求,未落地。

3. **MANIFEST canonical 判定与发布文档互相矛盾**
   - 发现: gen_manifest.classify 按 run-id 前缀判状态,两处直接错位:
     - `goose*` 前缀全标 pre-fix(excluded),但 goose 172504/173308 是**合法矩阵 run**,RESULTS.md 却发布了
       goose 分数(1.0/0.714)→ manifest 说 excluded、文档说 published;
     - opencode 171831(--format json 吞 prompt 时期的 0.0)无前缀被标 **canonical**,真正发布用的 0.429
       (verify_oc_e2b_fix2)反而标 pre-fix → 读者按 manifest 得到 opencode-e2b=0.0。
   - 怎么改: 去掉前缀启发式;canonical 状态由 run 时显式写入 score.json(或在 classify 读 score.json 的
     agent/model/failure_mode + 时间窗判定);RESULTS.md 表格与 MANIFEST 由同一脚本生成,单一事实源。

4. **run_id 模型标签坍缩(gemma4:12b 与 gemma4:e2b 同形)**
   - 发现: run_matrix.py:113 `md.split(':')[0]` 使两个不同模型格的 run_id 只差时间戳:
     `hummingbird_WF06_gemma4_m0_0828_175327`(12b) vs `..._181209`(e2b),无法程序化区分,
     也是第 3 条 classify 误判的根因之一。
   - 怎么改: run_id 用完整模型标识(冒号转下划线,如 `gemma4_12b`/`gemma4_e2b`),MANIFEST/MATRIX_MANIFEST
     按 agent+model+task 三元组索引。

6. **PNG 真伪校验仍未落地(前轮 P0#5)**
   - 发现: score_task 无 PNG 签名/IEND/PIL 解码检查,file_min_bytes 仍可被手拼字节骗过(goose 前科);
     judge_score 把 PNG 二进制当 utf-8 读成乱码塞进 judge prompt。当前矩阵 deterministic-only(无 judge),
     judge 部分暂不生效,但发布数据的图表真实性 0 覆盖。
   - 怎么改: 加 `image_valid` 确定性 check(PNG 签名 + IEND + PIL 可解码 + 最小分辨率);judge prompt 排除二进制产物。

7. **判分悬崖:1 词翻盘 + "12B<4B"反直觉**
   - 发现: hummingbird 12b=0.857 仅因 analysis.md 279/280 词差 1(score.json 实证);4b=1.0 → 矩阵出现
     12B<4B 反直觉结果。单 run 无方差,刀锋阈值直接改变论文叙事("4B=35B").
   - 怎么改: min_words 改软目标(按比例扣分)或阈值留 15% buffer;至少每格 2-3 次取中位;论文披露单 run +
     阈值敏感性。

8. **agent-mini 配置污染用户真机**
   - 发现: run_bench.py:80-95 直接改写 `~/.agent-mini/config.json`(temp=0、workspace 指向 bench workdir、
     memory off),跑完不还原;当前文件 workspace 仍指向 `...agentmini_WF06_.../workdir`。用户之后正常使用
     agent-mini 会一直带着基准配置。
   - 怎么改: bench 用隔离配置路径(agent-mini 若有 --config 则指向独立文件;否则 HOME/XDG 重定向),
     或跑前备份、跑后还原。
