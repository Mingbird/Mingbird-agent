# 设计:速度对比 / 流式输出 / 上下文梯度(2026-08-20)

## 背景
- 实测 gemma4:e4b 生成 **17.8 t/s**(硬件上限),300 字回复 ~17s。
- GUI 当前非流式:整段生成完才显示 → 用户"盯着空白等很久"。
- 用户要求:①对比 opencode/agentmini/自建软件速度 ②提高每次对话速度 ③上下文梯度扩到 256K ④流式显示思考过程+自动折叠+流式回答。

## 一、速度对比基准(18:00 后执行)
- **方案**:同一任务(如"用中文介绍你自己"),同一模型(gemma4:e4b),分别在
  - 自建 LocalAgent(GUI 发送)
  - opencode(若安装,`opencode run` 单轮)
  - agentmini(确认是什么工具;若本地没有则评估同类轻量 agent)
- **指标**:首字延迟(ttft)、token/s、总耗时、是否流式、CPU/内存占用。
- **预期结论**:token/s 三者接近(同一 GPU+模型);差距在 ttft 与流式 UX。重点把自建的**首字延迟压到 <2s** 并全流式。

## 二、流式输出(核心提速项,感知速度)
- **ollama_agent.py**:`call_chat` 增加 stream 模式。`agent_loop` 支持 `--stream` 时:
  - 调 `/api/chat` `stream:true`,逐 token 累积。
  - 每收到 chunk 通过回调(或队列)推送,由 GUI 实时渲染。
  - 普通 agent 任务仍走非流式(工具调用需要完整 JSON);仅 **纯对话回复**走流式。
- **agent_gui.py**:
  - 新增流式对话通道:收到 token 就 append 到当前助手气泡(typing 效果)。
  - **思考流**:模型 thinking tokens(如 `<thinking>…</thinking>` 或 gemma 的思考段)流式显示在一个可折叠面板里(标题"🤔 思考过程",细体/灰色小字)。
  - 思考结束 → 自动折叠(面板收起成一行,可手动展开)。
  - 随后**回答流式**逐字显示。
- 识别思考段:gemma4 是思考模型;ollama chunk 里思考内容可能以 `reasoning_content` 或 `thinking` 字段/特殊标记返回,需实测确认。备选:把"首段(直到第一个正式回答标记)"当思考。

## 三、上下文梯度(设置面板)
- 选项梯度:**16K / 32K / 64K / 128K / 256K**。
- GUI 设置面板 combobox 改为这 5 档(当前只有 ≤128K 且默认 16K)。
- 存 prefs(ctx),运行时透传 `AGENT_CTX`。
- **注意**:256K 对当前 13.7GB 机器 + 4B 模型会内存爆(32768 已死锁)。256K 是"预留":当 GUI 检测到内存不足以支撑所选 ctx 时,给提示"当前机型建议 ≤32K",但仍允许选大档供未来大模型/大内存机器使用。

## 四、实现顺序(18:00 后按作息推进)
1. 跑速度对比基准(openocode/agentmini/自建)→ 记录结果到 bench/。
2. 实现流式 + 思考流 + 自动折叠(ollama_agent + agent_gui)。
3. 上下文梯度 5 档。
4. 重打包 v0.10.0,让用户试用感知速度。

## 实测结果(18:00 后,新三强)
- **上下文上限**(本机 13.7GB,按模型实测):
  - qwen3.5:2b: **256K** 全开(36 t/s)— 原生 262144
  - gemma4:e2b: **128K** 全开(40 t/s)— 原生 131072
  - Mellum2-instruct-mxfp4_moe(7.0GB): **64K**(37 t/s);Q4_K_M thinking 版 8.1GB **超显存 OOM**(需 >8.5GB 空闲内存,日常不稳)
- **Mellum2 取舍**:用 mxfp4_moe(能跑);Q4_K_M thinking 版留作内存宽裕时的思考模式。
- 对比旧 e4b 32K 死锁 → 小模型+长上下文完全成立。
- 待办:①新三强从头跑 V 基准 ②流式+思考折叠 ③上下文梯度按此实测定档 ④GUI 模型列表更新 ⑤打包 v0.10.0。

## 扁平化 prefill 架构(标签驱动的按需加载,2026-08-20 晚)
- **问题**:任务 prefill = 全量工具定义 + 长 SYSTEM ≈ 几千 token;24k 上下文 prefill 是卡顿主因。
- **设计**:prefill 从"一整块"变成"基础块 + 按需拼装"。
  - BASE_SYSTEM 永远加载(角色/意图判断/安全/通用规则)。
  - 工具按类别打标签(文件/代码/网络/数据/办公/多媒体/记忆/通信)。
  - 路由器(轻量分类)从任务描述选出 1-3 个相关类别 → 只加载该类工具定义 + 提示碎片。
  - 预期 prefill 减 50-80%,prefill 提速。
- **安全**:分类不确定 → 加载宽默认(文件+代码+网络);agent 运行中可 enable_tools 补充;连续缺工具自动放宽。
- **实现**:CATEGORY_TOOLS + route_categories() + tools_for_categories(),接入 agent_loop 的 call_chat 与工具执行过滤。
- 产品更名:蚂蚁(撞阿里)→ **蜂鸟 / Hummingbird**(GUI 标题"蜂鸟 · 本地 AI 助手")。
