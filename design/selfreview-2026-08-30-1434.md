  "恢复能力"直接排名；③**竞品波次起跑前核实每个 runner 的 phase-2 语义**——蜂鸟不传 --new 走
  checkpoint 续跑（已冒烟验证），opencode/agent-mini/goose 同命令重启究竟是裸开新 session 还是

### P2-1（新发现，效率）MCP 探测缓存 TTL 设计缺陷：单进程内每 5 分钟全量重拉 stdio server
- **发现**：LH03-12b m0 单格 90min，transcript STDERR 出现 **13 次**"DuckDuckGo Search MCP
  Server running on stdio"，而全程 **0 次** MCP 搜索调用。根因在 `ollama_agent.py::mcp_manifest()`：
  内存缓存 TTL 300s 与磁盘缓存 TTL 同为 300s → 内存过期时磁盘必然同刻过期 → 每 300s 全量
  `_introspect_mcp_tools`（拉起 DDG stdio 进程 + tavily HTTP 连接）。磁盘缓存在单进程内零增值；
  13 次 node 启动纯浪费。WF 层 40min 格同样存在（~6 次/格），LH 90min 格放大。
- **怎么改（批末，不批中改）**：进程内缓存不过期（或以 mcp.json 的 mtime 失效），TTL 只管
  跨进程磁盘缓存。数行改动。顺带消除 STDERR 噪声对 transcript 取证的干扰。

### P2-2（新发现，质量）12b LH03 m0 末段疑似 edit→read 死循环；edit_file 无 no-op 检测
- **发现**：m0 最后 4 步 [43]–[46] = edit m08.py → read m08.py → edit → read，读回内容前两行
  完全相同；46 步里 m08 被提及 34 次、edit_file 共 18 次。疑似模型反复提交相同/无效编辑直到
  预算耗尽（transcript 截断显示，no-op 定论需全量核对）。m1 正在跑，可能复发。
- **怎么改（批末）**：①edit_file 检测 new==old 时返回"无变化"错误而非成功提示，直接打破循环；
  ②可加"连续 N 次相同工具调用 → 注入提示"。**注意**：这是小模型长视野退化的行为学证据，恰是
  LH 层要暴露的东西——修复前先把它作为 LH 分析素材记录，修复本身进 12b/4b 下一轮前。
