# LRAB-288: benchmark design rationale

This document is the design record of LRAB (Local Reliability Agent Benchmark):
what the 18 tasks are, why they exist, how scoring works, what was frozen when,
and where the design is strong or weak. It exists so a reader can decide
whether to trust the numbers without trusting us.

## 1. What LRAB measures (and does not)

LRAB measures whether an agent harness can take a small local model (2–35B)
through **multi-step work that leaves verifiable artifacts** — code that
compiles and passes tests, data analyses whose numbers cross-check, research
dossiers with real citations. It does **not** measure conversational quality,
knowledge, or single-shot function calling; those axes are covered by our
external anchors (τ²-bench retail, GAIA, BFCL v3 — see below).

Design constraints, chosen up front:

1. **Deterministic scoring.** Every check is a file/content/execution check
   run by a script. There is no LLM judge anywhere in the LRAB pipeline, and
   the scorer never sees which harness produced an artifact.
2. **Wall-clock honesty.** Timeouts score 0. A model that "would have finished
   given more time" gets no credit; local users care about finishing.
3. **Harness neutrality.** Task prompts carry no harness-specific vocabulary
   (planning is requested as *"todo tool if available, otherwise plan.md"*).
   An audit of the harness source found zero task-specific hardcoding.
4. **Pre-registration.** Retry policy, aggregation and budgets were fixed and
   written down before the final matrix ran (METHODS §2, §6).

## 2. Task ladder — 4 tiers × 18 tasks

Tasks were generated by versioned generator scripts (`gen_tasks.py`,
`gen_lhab.py` — both in the repo) into a difficulty ladder:

- **T1 retrieval (WF-01/02)** — locate and extract from supplied fixtures.
- **T2 synthesis (WF-03..06)** — implement features, synthesize data, write tests.
- **T3 workflow (WF-07..15)** — multi-step workflows: web research with real
  search, profiling and optimization, refactors, comparison dossiers.
- **T4 long-horizon (LH-01..03)** — deep dependency chains across many
  artifacts; LH-03 doubles as a kill-and-resume stress test (checkpoint
  continuity at 50% budget).

Each task specification carries: `domain`, `fixtures` (input data the agent
must ground in), `plan_steps` (minimum credible plan), `milestones`
(checked intermediate artifacts), `final_artifacts` (checked deliverables),
a per-task `judge_rubric`, and the authoring-time budget. The generator
scripts and frozen fixtures are published — every check is readable before
you run anything.

**Check vocabulary** (all deterministic, all scripted): `exists`, `contains_any`
(grounded in fixture ground truths — e.g. LH-01's per-batch statistics are
compared against values precomputed from the 5000-row fixture),
`min_words`, `min_urls`, `structure` (required sections),
`python_compiles`, `contains_groups` (cross-artifact numeric consistency).
Milestone artifacts score against the plan the model itself declared,
so partial credit tracks its own proposed process.

## 3. Budgets

Authoring-time budgets (WF 60 min / LH 90 min in the task JSON) were raised to
**90 min (WF) / 180 min (LH) at the protocol freeze**, pre-registered before
the final matrix began (METHODS §6 records the lineage). Timeouts are scored 0
only after budget adequacy for that model is verified — the one 35B timeout in
the final matrix is published with its full transcript.

**Reading.** On 2B and 12B the Mingbird-vs-each-competitor difference is
significant under Wilcoxon with Holm correction across all pairings. On 4B the
goose and opencode comparisons are significant, while agent-mini — whose 4B
tier is its best segment — is not (raw p = 0.074). On 35B the field compresses:
many ties reduce the effective pair count, and Mingbird-vs-goose/opencode do
**not** reach significance (p≈0.07–0.14) despite positive means. We state that
bound rather than hiding it; the claims we make about "the models people
actually run" (2B–4B) are exactly the segments where the separation is starkest.

## 5. Provenance & freeze discipline

- Tasks were generated and frozen before any final-matrix run; the final matrix
  executed from a **frozen snapshot** of the harness (`fp-0902`), so no code
  change during the run could alter the apparatus (audited post-publication).
- The published CSV's attempt directories, transcripts and scorer outputs ship
  alongside; every table recomputes from the CSV.
- An external audit (source-level) found no task-name hardcoding in the
  harness and no use of Mingbird-only tools (memory/skills/batch dispatch)
  in any of the 72 final transcripts.

## 6. Known deviations & threats to validity

- **n = 18 tasks per model.** Power is limited; the 35B layer is tie-heavy and
  does not separate harnesses statistically. Treat 35B columns as indicative.
- **Self-designed tasks.** LRAB was designed by us — which is why generators,
  fixtures, rubrics, transcripts and the scorer are all published and every
  number recomputes. The external anchors (τ²-bench retail 0.746 vs 0.430;
  GAIA; BFCL v3) exist because a self-built benchmark alone cannot settle the
  question.
- **Configuration asymmetries (disclosed).** goose exposes no context knob
  (default context); agent-mini's memory was disabled by the runner config.
  Both are recorded in METHODS §5.
- **Two 2B cells** were re-run post-batch for a parse-failure investigation
  under the same latest-attempt-wins rule (+0.011 overall; 0.883 without
  them). Ranking is identical under either convention.
- Single machine, Windows, one Ollama build. Cross-machine variance is
  unmeasured; the external anchors run the same protocol on their own
  machines where applicable.
